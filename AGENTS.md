## Current Architecture Decisions (CRITICAL)
- **Active Backend**: `API_PROXY_SCHEME=python` is frozen as the sole active and supported backend path.
- **Python Authoritative**: Python (`api/`) is the single source of truth for current permission, RBAC, and tenant refactoring.
- **Go Backend Deprecation**: Go (`internal/`) permission and authentication paths are INACTIVE for current features.
- **No Dual Sync**: Do NOT attempt to revive or edit Go backend code for symmetry.
- **Error Response Standard**: Permission denials MUST follow RAGFlow standard `HTTP 200` with `code=108` (`get_error_data_result`) for seamless frontend Toast and error handling.
- **Frontend HTTP Payload Contract**: `umi-request` calls MUST wrap payload bodies in `{ data: body }` (e.g., `request.put(url, { data: { role } })`), otherwise parameters fail validation with `code=101`.

## Tenant & RBAC Model (CRITICAL)

The tenant role hierarchy is strictly enforced as:

**OWNER > ADMIN > NORMAL**

### Role Definitions
- **OWNER**: Tenant creator/owner. Full tenant authority, manages administrators and overall tenant settings.
- **ADMIN**: Granted tenant-management permissions by RBAC layer. Manages members and assigned configurations; cannot override OWNER.
- **NORMAL**: Standard tenant user. Cannot manage members, tenant-level providers, or system settings.

### Tenant Context & Multi-Tenancy Architecture
- **Active Tenant Context**: NEVER assume `user.id == tenant_id` for non-owner users. All workspace operations MUST be scoped to the `active_tenant_id` resolved via `TenantService.resolve_config_tenant_id` or active session/request context.
- **Joined Tenant Access**: NORMAL members without personal tenants inherit read-only access to their joined tenant's shared model configurations and knowledge bases (`resolve_config_tenant_id`).
- **Backend Enforcement**: Frontend UI/component hiding is NEVER an authorization boundary. Sensitive endpoints MUST enforce `@require_tenant_admin`.
- **Visibility vs Ownership**: `visibility` (e.g. `me` vs `team`) DOES NOT equal ownership.
- **Access vs Management**: Read/query permission DOES NOT imply permission to modify, delete, transfer, or manage.
- **Decoupled Roles & Attributes**: Tenant roles (`role` -> authorization) and organizational attributes (`department_id`, `title` -> profile) MUST be handled via distinct endpoints (`PUT /role` vs `PUT /profile`).
- **Private Visibility Semantics**: `private` (`permission='me'`) knowledge bases are visible to the **Creator + Tenant Owner/Admin** for enterprise governance and auditing.

### Member Removal & Asset Reassignment (P3-01a/b Rules)
- **Immediate Access Revocation**: Once the removal transaction commits, the removed user MUST lose every read, write, retrieval and model-execution permission in that workspace. Subsequent requests targeting it MUST return `HTTP 200` + `code=108`, including requests made with an old JWT, Cookie, resource URL or workspace-scoped API credential. A rejected workspace selection MUST NOT silently fall back to another workspace and execute there; memberships in other workspaces remain independent.
- **Atomic Reassignment**: In ONE database transaction, validate the recipient, transfer every dataset, agent canvas and chat assistant owned by the departing member in the workspace, revoke membership and workspace-specific grants, and invalidate the stored workspace selection. The recipient MUST be the workspace OWNER or an explicitly designated, active ADMIN of that SAME workspace. If any transfer fails or the recipient is invalid, roll back the entire operation; never report successful removal with orphaned assets.
- **Preserve Resource Boundaries**: Rebind the actual ownership fields (including `created_by` where it is the authorization subject), retain the resource's workspace and private/custom visibility, and audit the original owner, recipient and operator. Never make a private asset public to solve ownership, silently delete assets, or transfer assets from another workspace. Historical authorship belongs in the audit trail rather than in a field that still grants the removed user access.
- **Revocation Enforcement**: Revalidate current membership on every workspace request; creator identity and cached grants MUST NOT bypass revocation. Invalidate authorization caches and fence/cancel queued or running work for that membership before its next protected access or provider call. Cache invalidation alone is not the security boundary: use current authoritative membership or a revocation version so an old cache cannot restore access.

### Model Execution & Key Isolation (P4-04 Rules)
- **Owner Scope Resolution**: A NORMAL member with permission to invoke an assistant uses its owning WORKSPACE's model/provider configuration through `TenantService.resolve_config_tenant_id`. Resolve the assistant's authoritative tenant first, then bind the resolved configuration to that tenant. The workspace paying for execution is distinct from the assistant creator and from the caller's personal tenant; borrowing a provider does not make another user's private assistant readable.
- **Authorize Before Resolving**: Check live workspace membership and assistant access before loading credentials. Validate every requested model/provider instance against the assistant's owning tenant and allowed execution configuration. Use the resolver's actual input contract; never feed an already-resolved tenant ID through a user-ID resolver, fall back to the caller's unrelated personal provider, or search all joined tenants for a matching model name. Unauthorized scope/model selection returns `HTTP 200` + `code=108` before any provider call.
- **Execution Is Not Configuration Access**: Borrowing a provider is a server-side execution capability only. NORMAL users may receive allowed model metadata and redacted configuration, but MUST NOT receive plaintext keys or gain provider-management rights. The same tenant and credential boundary applies to chat, embedding, reranking, tool calls and agent subcalls, including caller-supplied model IDs and retries.

## Rate Limiting & API Usage Quota Control

The current implementation enforces **model-call attempts, tokens and (when a model states pricing) cost**: NORMAL defaults are 20 per rolling minute, 1,000 calls per UTC day, 20,000 calls per UTC calendar month, 200,000 tokens per day and 4,000,000 tokens per month, with cost limits defaulting to 0 = **not enforced** because pricing is optional per model. OWNER/ADMIN are explicitly exempt from these employee limits, but never from live membership validation. The day and month boundaries are midnight and the first of the month in the **workspace's own timezone** (`WorkspaceBudget.timezone`, default `UTC`). `GET/PUT /tenants/<tenant_id>/usage-budget` reads/updates every limit plus the timezone (OWNER/ADMIN only, audited); a PUT may carry any subset of the fields. Failed/cancelled attempts remain charged; the durable SQL counters survive Redis loss, and `workspace_usage_ledger` records every attempt's reserved bound and its settlement. Verified live on the deployed stack (see the milestones in Progress Base): rate denial, the OWNER exemption, per-attempt charging, token settlement to the provider-reported usage of a dataset-bound turn, the workspace-calendar boundary (`Pacific/Kiritimati` charged a `2026-09-27` period while UTC was still `2026-09-26`), a token denial before dispatch, cost settled from a model's own pricing, a worker's embedding calls charged to the member who queued the parse, a queued job fenced after that member was removed, and DENIAL - not unmetered access - when the budget store cannot be reached. Two things this is still NOT: a monetary cap (counts and tokens are not billing) and blanket coverage of every detached job shape. The fuller design requirements are:
- **Redis Rate Limiting**: Use atomic Redis Lua operations for a rolling-window counter keyed by `(workspace_id, user_id)` across API workers. A configurable example for NORMAL users is 20 admitted requests per rolling 60 seconds. Share the budget across sessions, assistants and credentials belonging to that user; switching applications or opening concurrent requests MUST NOT reset or multiply it. Authentication and tenant authorization run first. The rolling minute is deliberately zone-independent; only the day/month reset boundary follows the workspace timezone.
- **Daily / Monthly Quotas**: Define explicit per-user/workspace limits and units for requests, input/output tokens and, when pricing is available, cost. Enforce both daily AND monthly caps using a configured workspace timezone and documented reset boundaries. Persist a usage ledger and reconcile Redis counters from it so eviction or restart cannot reset a spent quota. Units in this codebase: calls are attempts, tokens are prompt+completion as reported by the provider, and cost is stored as **micro-USD** (`cost_micros`, 1e-6 USD) so the ledger needs no floats - a model's `extra.price_input_per_million` / `price_output_per_million` (USD per million tokens) is numerically micro-USD per token and is used as-is. A limit of 0 on the token/cost dimensions means "not enforced"; the call dimensions keep a positive floor.
- **Reserve Before Spending**: At the common provider-dispatch boundary, atomically reserve bounded usage before a billable call, then settle actual usage and release unused reservations idempotently by request/call ID. Concurrent calls MUST NOT oversubscribe a quota; retries, streaming, cancellation and failures MUST NOT double-count or erase provider usage already incurred. Limit output tokens and agent iterations, and check/reserve every billable subcall against the initiating user's workspace budget so one admitted request cannot fund an unlimited agent loop. This codebase's shape of that rule: `common.model_budget.budgeted` reserves ONE call plus `prompt estimate + min(max_tokens, 8192)` tokens (and the matching cost bound) before the dispatch, `LLMBundle` reports the provider's usage back through `record_dispatch_usage`, and the reservation is settled DOWN to the actual (topped up if the provider reported more). Settlement is idempotent per reservation id, so a stream closed early, a retried callback or a duplicate provider round cannot charge twice; extra LiteLLM retries/tool rounds are charged as extra CALLS and their reservation is closed as "no usage of its own". A dispatch that reports nothing keeps its WHOLE reservation (`status=unsettled`) - a timeout does not prove the provider spent nothing.
- **Standard Denial**: Exceeding frequency, call, token or cost quota MUST return RAGFlow `HTTP 200` + `code=108` before dispatch, with a plain-language Toast message such as `请求过于频繁，请稍后重试`, `今日/月度使用额度已用尽` or `今日/月度 Token 额度已用尽` / `今日/月度费用额度已用尽`. Do not substitute HTTP 429 or leak provider errors/keys. Where a stream has already started, stop further calls and use the existing stream error envelope carrying `code=108`; an already-sent HTTP status cannot be changed.
- **Detached Work Attribution**: A queued job MUST carry the identity of the member who caused it, so the model calls a worker makes are metered against that member's quota in the job's workspace instead of against nobody. Persist it (`task.initiator_user_id`) from the AUTHENTICATED caller - never from the end-user id a request may carry for provider tracing - and install it in the worker through `workspace_budget_service.enter_detached_job`, which revalidates the membership: a queued job whose initiator has since been REMOVED is refused (`发起该任务的成员已不在工作区...`) before it can spend, and a legacy row with no recorded initiator is attributed to the workspace owner. A job whose workspace cannot be established at all stays unmetered and logs a warning; do not fail it, or pre-existing task shapes break.
- **Failure & Administration Policy**: If the budget store is unavailable, fail closed for workspace-funded billable calls with a controlled `HTTP 200` + `code=108` service-unavailable message; do not grant unmetered access. Only authorized OWNER/ADMIN users may configure limits in their own workspace, with audited changes. A role change or alternate credential MUST NOT silently erase accrued usage; any role-specific exemption must be explicit. An unparseable stored timezone falls back to UTC with a warning rather than refusing every call: it moves a reset boundary, it does not decide whether a limit applies.

- **Rule-Based Table Extraction, Over-Page Merge & Header Injection**: Cable tables are where the corpus hurts: a large parameter table (Q/GDW 73286.3 表1) reaches the answer model as a few text lines, and a table whose vertical rules are simply not printed is invisible to a lines-based finder - both end up as prose, and a row like `3x630mm² 26.0mm` has no column to belong to. ### Addendum 2 (same round): decomposition, routing and ordering chain

## 13. Second forensics addendum: decomposition, routing and the ordering chain in detail

Facts from the decomposition-path forensic pass (same round, read-only). One of them **refines the
interpretation** in section 8; the rest add mechanism. None of them changes the headline.

### 13.1 The LLM decomposition call, precisely

- The single LLM call is `gen_json(rendered, "Output:\n", chat_mdl)`, and `gen_conf` keeps its `{}` default,
  so the request body carries no `temperature`, `top_p`, `seed`, `max_tokens` or `stream` — provider defaults
  apply. `_clean_conf` only filters keys; `_apply_model_family_policies` only removes sampling keys for some
  families and never injects a temperature or seed.
- The cache key is `xxh64(llm_name + system_prompt + user_prompt + gen_conf)` with a **24 h** TTL, which is why
  the live log shows byte-identical sub-query lists 26 minutes apart. This is the only stabiliser.
- `parse_sub_queries` truncates to `max_sub_queries`, so two cache-miss answers can differ in **cardinality** as
  well as content. `max_sub_queries == 1` still calls the LLM; only `<= 0` disables it.

### 13.2 REFINEMENT: `chat_mdl = None` does not reduce the pipeline to a single route

Two **LLM-free** routes fire regardless of the chat model: the comparative side routes
(`comparative_routes`, documented "No LLM call") and the normative-prose clause route (`clause_route`). The
route list is `[question] + sub_queries + side_routes + [targeted]`.

So the series A versus series B difference in section 8 is attributable specifically to the
**LLM-generated sub-queries**, not to the entire route set. Series B still had side routes and still returned
12-20 candidate pools; it simply lacked the model-written sub-queries. This does not change the conclusion
(the divergence is a configuration difference, not randomness) but it makes the attribution precise, and it
means a cold-cache comparison is the only way to observe raw LLM sampling variation.

### 13.3 `routes_top_k` provenance, completed

- `NUMERIC_TOP_K = 20`, `REVISION_TOP_K = 12`, `CONCEPTUAL_TOP_K = 10` (`query_router.py:69-73`), matched in rule
  order numeric -> revision -> conceptual. The numeric rule fires on unit/number/model/table shapes such as
  `220 kV` or `800 mm2`, which is why the business-critical queries in this round ran at 20 and the others at 12.
- `dialog_service.py` does **not** pass `routes_top_k`, so the log reads `(configured 0.5 / 12)` — `0.5` is
  `dialog.vector_similarity_weight`, `12` is the signature default. The pipeline then applies
  `routes_top_k = max(decision.routes_top_k, resolve_final_top_n(final_top_n))` (`pipeline.py:236-242`).
- Ruled out with evidence: signature default, config file, environment variable, and decomposition (it has no
  such field). The warning fires whenever the routed value leaves the recommended `(10, 15)` band, so for a
  numeric-shaped question it fires on every single request — by design, not as a symptom.

### 13.4 Pool-dependent branching is the amplification mechanism

Two branches are decided by the pool rather than by the question, and both are deterministic in themselves:

1. Every route makes a first call at `similarity_threshold` and, if that returns nothing, a **second call at
   `RECALL_FLOOR = 0.2`** (`multi_route.py:247/256`), which changes the ES `similarity` filter.
2. `core_document_followup` triggers a **second whole retrieval pass over up to 3 extra routes** when the first
   pool lacks core prose (`MIN_CORE_PROSE_PASSAGES = 4`, `MAX_CORE_DOCUMENT_ROUTES = 3`,
   `pipeline.py:56/63/317-326`), then re-merges.

Because both are functions of the pool, a small upstream change can change the route set, which then changes
every downstream tie. This is the concrete route by which modest perturbations become whole-window
differences, and it is consistent with the live `0 prose / 12 table` versus `11 prose / 1 table` observation.

### 13.5 The ordering value is not the raw cosine

`rank_score = base * penalty * boost` (`rerank.py:310-321`), with `base = rerank_score or similarity`,
`HOLLOW_TABLE_PENALTY = 0.6`, `VALUE_LIST_PENALTY = 0.8`, `core_document_boost = 1.15`,
`VALUE_PAIRING_BOOST = 1.3`. Every factor is a constant and the product is deterministic **for a fixed pool** —
but each factor depends on pool composition (table versus prose mix, whether a table pairs the question
figures, which document is core). Pool-dependent, not random.

`select_context` never re-sorts: it returns `[chunk for chunk in ordered if chunk_key(chunk) in chosen_keys]`
(`rerank.py:563`) after claiming slots in a fixed priority order — one slot per route, one per compared
document, a prose floor, then score fill — with `math.ceil`-derived quotas. Deterministic given the pool, and
the output order is the pool order.

### 13.6 Sizing and the hard guard

`rerank_candidates_count = max(configured or 64, top_k)` (`multi_route.py:294-295`), so the ES candidate fetch
scales with the routed `top_k`; and `page * page_size > rerank_candidates_count` (`search.py:745`) turns a
mismatch into a **hard failure** rather than a degraded result — the failure mode observed earlier in this
workstream when the parameter was passed explicitly as `None`.

### 13.7 Hash-order risk closed

`PYTHONHASHSEED` is not pinned, but no hash-order-dependent construct reaches the candidate order: every `set`
use on this chain is membership-only or truthiness-only (`resolve_compared_documents` and
`resolve_core_documents` return sets, but consumers wrap them in `frozenset`, test membership, or iterate a
list built from the already-ordered pool); there is no `list(set(...))` or `sorted(set(...))` in the retrieval
package; dict iteration is insertion order derived from lists; the only hashing is a content-addressed
`hashlib.sha1` used for table-family keys.

### 13.8 Complete ordering inventory

The package has exactly three ordering sites on the candidate path — `multi_route.py:195` (cross-route merge),
`rerank.py:321` (`rank_score`) and `search.py:848` (stable `argsort` inside the store). Display-only sorts and
the `sorted(policy.question_values)` canonicalisation do not affect candidate order. **None of the three has a
tie-breaker**; ties fall through to insertion order, which decomposes into route order (preserved by
`asyncio.gather`) times per-route store order.

Effect on the conclusions: unchanged headline. A changed input can enter at the LLM sub-queries (on a cache
miss) and at two pool-dependent branches; once the inputs and the pool are fixed, every ordering step is a pure
function. No fix, no parameter change, no index write.
